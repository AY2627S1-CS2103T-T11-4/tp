Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
    • Parser: Parsers for user inputs
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command deleteStudent 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, StudentListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Student objects from the model.

How the Logic component works

Command execution
  1. The UI calls Logic.execute(commandText). LogicManager passes the command text to BrotherGymParser, which returns the corresponding Command object.
  2. LogicManager executes the command with the Model. Commands can read or update model data and return a CommandResult.
  3. After a command executes successfully, LogicManager saves the BrotherGym data through Storage and returns the CommandResult to the UI. MainWindow displays the result's feedback; parsing, command, and storage errors are also displayed there.
Interaction with the UI

Logic exposes the filtered student list, the current student and its read-only observable property, and GUI settings to the UI.

  • Student list and selection: The UI observes the filtered student list so it reflects changes to the student filter. MainWindow observes the current-student property and updates the student selection and workout-plan panel when it changes.
  • GUI settings: The UI reads these settings when initializing the window and updates them through Logic when exiting.
  • Workout plans: The home command shows all students and clears the current selection. Plan commands operate on the currently selected student.

How the parsing works:

  • When called upon to parse a user command, the BrotherGymParser class creates either an XYZCommandParser or a SingleIndexCommandParser
    • addStudent, addPlan, editStudent and editPlan commands each have a dedicated XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddStudentCommandParser),
    • viewStudent, viewPlan, deleteStudent and deletePlan commands are SingleIndexCommands that only parse a single index, hence they use the same generic SingleIndexCommandParser
    • both types of parsers implement the Parser interface so they can be treated similarly where appropriate, for example during testing.
  • The parser class uses a few dependencies to parse the user input into a valid command object (e.g. AddStudentCommand, DeleteStudentCommand):
    1. The user input string is passed into ArgumentTokenizer to create a ArgumentMultimap object to store the entered arguments.
    2. The ArgumentValidator ensures that the ArgumentMultimap contains the correct arguments for the command.
    3. The arguments in the ArgumentMultimap is then passed into the relevant ParserUtil class to generate the objects required for creating the Command object
  • The BrotherGymParser returns that object as a Command object.

### Model component **API** : [`Model.java`](https://github.com/se-edu/addressbook-level3/tree/master/src/main/java/seedu/address/model/Model.java) The `Model` component, * stores the BrotherGym data i.e., all `Student` objects (which are contained in a `UniqueStudentList` object). * stores the `Student` objects selected by the current filter, such as search results, in a separate _filtered_ list. It exposes this list as an unmodifiable `ObservableList` that the UI can observe and bind to, so the UI updates when the list changes. * stores a `UserPrefs` object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a `ReadOnlyUserPrefs` object. * does not depend on any of the other three components (as the `Model` represents data entities of the domain, they should make sense on their own without depending on other components)
**Note:** The alternative, arguably more object-oriented, design below keeps a unique list of tags in `BrotherGym`, and each `Student` references tags from that list. This lets `BrotherGym` maintain one `Tag` object per unique tag instead of each `Student` holding its own `Tag` objects.
### Storage component **API**: `seedu.address.storage.Storage` (defined in `src/main/java/seedu/address/storage/Storage.java`). The `Storage` component persists BrotherGym data and user preferences as local JSON files. It converts stored data into model objects when the application starts and writes model data back to disk when requested by `LogicManager` or `MainApp`. #### Structure and responsibilities * `Storage` exposes methods to read and save BrotherGym data and user preferences, and to retrieve their file paths. Callers use this interface without handling JSON conversion themselves. * `StorageManager` implements `Storage` and delegates operations to `JsonBrotherGymStorage` and `JsonUserPrefsStorage`, with one storage object per file. * `JsonBrotherGymStorage` handles the BrotherGym data file, using JSON adapters to keep its stored representation separate from the model. * `JsonUserPrefsStorage` reads and writes `UserPrefs` directly, without a separate JSON adapter. Both file storage classes use `JsonUtil` from the `Commons` component for JSON file access. Storage depends on the model types it persists; the model does not depend on Storage. #### Stored data and file locations `MainApp` supplies the following paths when constructing the storage objects. Both paths are relative to the application's working directory. | File | Contents | Representation | |------|----------|----------------| | `data/brothergym.json` | All students, their contact details, tags, and workout plans | `JsonSerializableBrotherGym` and its nested adapters | | `preferences.json` | GUI settings, including window size and position | `UserPrefs` | BrotherGym data is stored as a top-level `students` array. The following example shows one student with one workout plan: ```json { "students": [ { "name": "Alex Tan", "phone": "91234567", "email": "alex@example.com", "address": "123 Gym Road", "tags": ["beginner"], "workoutPlans": [ { "title": "Leg day", "workoutDescription": "Squats: 3 sets of 10 reps", "date": "2026-10-15", "tags": ["strength"] } ] } ] } ``` Workout dates use ISO local-date format (`yyyy-MM-dd`). `JsonAdaptedWorkoutPlan` converts between this string and the model's `WorkoutDate` using the system's default time zone. Tags are JSON strings; their type is determined by whether they belong to a student or a workout plan. Missing or `null` tag lists and student workout-plan lists are treated as empty lists. Jackson ignores unknown JSON properties. These choices allow older files without the optional lists to load, but required student fields and workout-plan fields must still be present. #### Loading and validation During startup, `MainApp` first loads preferences through `JsonUserPrefsStorage`, then constructs `StorageManager` and reads BrotherGym data through the `Storage` interface. The sequence below shows a successful BrotherGym read; nested adapter conversions are summarized in the note. 1. `StorageManager` delegates `readBrotherGym()` to `JsonBrotherGymStorage`. 1. `JsonUtil.readJsonFile()` reads the file and deserializes it into `JsonSerializableBrotherGym`. 1. `JsonSerializableBrotherGym.toModelType()` creates an empty `BrotherGym` and calls `JsonAdaptedStudent.toModelType()` for each stored student. Each student adapter validates its contact fields, converts its tags using `JsonAdaptedTag.toStudentTag()`, and calls `JsonAdaptedWorkoutPlan.toModelType()` for each stored workout plan. Each workout-plan adapter checks required fields, parses its date, and converts its tags using `JsonAdaptedTag.toWorkoutPlanTag()` before constructing a `WorkoutPlan`. The student adapter then collects these plans into a `WorkoutPlansList` and constructs a `Student` using the converted contact fields, tags, and plans. Finally, `JsonSerializableBrotherGym.toModelType()` adds each reconstructed student to the `BrotherGym`. This chain assembles smaller model objects into larger ones: tags and workout fields form workout plans; contact fields, student tags, and workout plans form students; students form the complete `BrotherGym`. Model constructors also enforce their own constraints. 1. `JsonSerializableBrotherGym` rejects duplicate students using the model's `hasStudent()` check. Only a completed conversion is returned as `Optional`; a failed conversion does not return a partially loaded model. The caller decides what to use when data cannot be loaded: | Read outcome | Storage behavior | Startup behavior in `MainApp` | |--------------|------------------|-------------------------------| | BrotherGym file is missing | Returns `Optional.empty()` | Initializes the model with sample data | | BrotherGym file cannot be read or deserialized | Throws `DataLoadingException` | Logs a warning and initializes an empty BrotherGym | | An adapter reports an `IllegalValueException`, such as an invalid phone number or duplicate student | Wraps it in `DataLoadingException` | Logs a warning and initializes an empty BrotherGym | | Preferences are missing or loading throws `DataLoadingException` | Returns `Optional.empty()` or propagates the exception | Uses default preferences | The fallback above applies to `DataLoadingException`. Unchecked exceptions from model constructors or malformed nested values are not all translated into this exception by the current adapters. After initializing preferences, `MainApp` attempts to save them, including defaults if a fallback was used. Loading BrotherGym data itself does not write a data file; sample or empty data is saved on the next successful command. #### Writing data: from model objects to JSON Writing proceeds from the complete `BrotherGym` down to its nested objects. `JsonBrotherGymStorage.saveBrotherGym()` accepts the model through its `ReadOnlyBrotherGym` interface and constructs a separate tree of JSON adapters. This conversion uses constructors that accept model objects: 1. **BrotherGym:** `new JsonSerializableBrotherGym(brotherGym)` reads `brotherGym.getStudentList()` and creates a `JsonAdaptedStudent` for each student. These adapters form its `students` list. 1. **Students:** `new JsonAdaptedStudent(student)` extracts the student's name, phone, email, and address as strings. It converts each student tag into a `JsonAdaptedTag` and each plan in the student's `WorkoutPlansList` into a `JsonAdaptedWorkoutPlan`, collecting them into its `tags` and `workoutPlans` lists. 1. **Workout plans:** `new JsonAdaptedWorkoutPlan(plan)` extracts the title and workout description as strings, formats the date using `formatDateForStorage()`, and creates a `JsonAdaptedTag` for each workout-plan tag. 1. **Tags:** `new JsonAdaptedTag(tag)` copies the tag's name. The same adapter accepts both `StudentTag` and `WorkoutPlanTag`; its position in the adapter tree preserves which object owns the tag. 1. **JSON output:** Once the adapter tree is complete, `JsonUtil.saveJsonFile(data, filePath)` uses Jackson to serialize it into formatted JSON. The adapter lists become JSON arrays, and `JsonAdaptedTag` uses `@JsonValue` to serialize each tag as a string. `FileUtil` then writes the JSON text to the destination file in UTF-8. The resulting structure matches the example under **Stored data and file locations**: the top-level `students` array contains student objects, each student's `workoutPlans` array contains workout-plan objects, and both students and workout plans have their own `tags` arrays. The adapters copy values from the model without modifying it. #### Automatic saving and write failures `LogicManager.execute()` calls `storage.saveBrotherGym(model.getBrotherGym())` after a command executes successfully and before returning its `CommandResult`. This happens for every successful command, including commands that only change the view. Parsing errors and command execution errors prevent this save step from being reached. Before conversion, `JsonBrotherGymStorage` creates the data file and any missing parent directories. Each save replaces the existing file contents with the entire BrotherGym rather than appending an individual change. `MainApp.stop()` separately saves the current user preferences on shutdown. If saving BrotherGym data throws an `IOException`, `LogicManager` reports a `CommandException`; an `AccessDeniedException` produces a message about insufficient write permissions. The command has already executed at this point, so a failed save does not roll back its changes in memory. Preference save failures are logged by `MainApp`.
**Persistence limitations:** Writes currently go directly to the destination file, without an atomic file replacement or automatic backup. A write failure can leave the file incomplete. After startup falls back to an empty BrotherGym, the next successful command attempts to overwrite the existing data file with the current in-memory data.
Workout plans store their `status` as `PENDING`, `COMPLETED`, or `OVERDUE`. Reading a file preserves the saved status without recalculating deadlines. Older files with a missing or null status default to `PENDING`; invalid status values cause a data-loading error. Date-based statuses are refreshed when the user runs `viewStudent`. ### Common classes Classes used by multiple components are in the `seedu.address.commons` package. -------------------------------------------------------------------------------------------------------------------- ## **Implementation** This section describes some noteworthy details on how certain features are implemented. ### \[Proposed\] Undo/redo feature #### Proposed Implementation The proposed undo/redo mechanism is facilitated by `VersionedBrotherGym`. It extends `BrotherGym` with an undo/redo history, stored internally as an `brotherGymStateList` and `currentStatePointer`. Additionally, it implements the following operations: * `VersionedBrotherGym#commit()` -- Saves the current BrotherGym state in its history. * `VersionedBrotherGym#undo()` -- Restores the previous BrotherGym state from its history. * `VersionedBrotherGym#redo()` -- Restores a previously undone BrotherGym state from its history. These operations are exposed in the `Model` interface as `Model#commitBrotherGym()`, `Model#undoBrotherGym()` and `Model#redoBrotherGym()` respectively. Given below is an example usage scenario and how the undo/redo mechanism behaves at each step. Step 1. The user launches the application for the first time. The `VersionedBrotherGym` will be initialized with the initial BrotherGym state, and the `currentStatePointer` pointing to that single BrotherGym state. Step 2. The user executes `delete 5` command to delete the 5th student in the BrotherGym. The `delete` command calls `Model#commitBrotherGym()`, causing the modified state of the BrotherGym after the `delete 5` command executes to be saved in the `brotherGymStateList`, and the `currentStatePointer` is shifted to the newly inserted BrotherGym state. Step 3. The user executes `add n/David …​` to add a new student. The `add` command also calls `Model#commitBrotherGym()`, causing another modified BrotherGym state to be saved into the `brotherGymStateList`.
**Note:** If a command fails its execution, it will not call `Model#commitBrotherGym()`, so the BrotherGym state will not be saved into the `brotherGymStateList`.
Step 4. The user now decides that adding the student was a mistake, and decides to undo that action by executing the `undo` command. The `undo` command will call `Model#undoBrotherGym()`, which will shift the `currentStatePointer` once to the left, pointing it to the previous BrotherGym state, and restores the BrotherGym to that state.
**Note:** If the `currentStatePointer` is at index 0, pointing to the initial BrotherGym state, then there are no previous BrotherGym states to restore. The `undo` command uses `Model#canUndoBrotherGym()` to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Similarly, how an undo operation goes through the `Model` component is shown below: The `redo` command does the opposite — it calls `Model#redoBrotherGym()`, which shifts the `currentStatePointer` once to the right, pointing to the previously undone state, and restores the BrotherGym to that state.
**Note:** If the `currentStatePointer` is at index `brotherGymStateList.size() - 1`, pointing to the latest BrotherGym state, then there are no undone BrotherGym states to restore. The `redo` command uses `Model#canRedoBrotherGym()` to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.
Step 5. The user then decides to execute the command `list`. Commands that do not modify the BrotherGym, such as `list`, will usually not call `Model#commitBrotherGym()`, `Model#undoBrotherGym()` or `Model#redoBrotherGym()`. Thus, the `brotherGymStateList` remains unchanged. Step 6. The user executes `clear`, which calls `Model#commitBrotherGym()`. Since the `currentStatePointer` is not pointing at the end of the `brotherGymStateList`, all BrotherGym states after the `currentStatePointer` will be purged. Reason: It no longer makes sense to redo the `add n/David …` command. This is the behavior that most modern desktop applications follow.
